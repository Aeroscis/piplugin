# Windows D3D 窗口交互式缩放（flip 模型）

> 适用范围：任何用 **DXGI flip 模型交换链**渲染、并在运行时改变窗口尺寸的 Win32 应用。
> 本文记录「拖动边框时窗口内容被瞬时缩放 / 拉伸 / 抖动」这类问题的**判定方法、根因与解法**。
> 它是平台机制知识，不绑定某个 bug——`docs/todo/tests.md` 第 7 条是本仓库里该问题的一次具体修复。

## 1. 症状与判定

典型症状：拖动窗口边框缩放时，画面里**有细节的内容**（面板、文字）会横向缩窄或拉伸一下再弹回，
幅度与拖动速度/步长成正比；而作为**子窗口 HWND** 嵌入的区域（如 Qt 插件）纹丝不动。

**关键判定：用"不被缩放的东西"做参照物。** 子窗口 HWND 由窗口管理器定位，
不参与交换链的缩放；所以：

- 子窗口位置不动 + 绘制内容尺寸变化 ⇒ **DWM 在缩放帧**，不是应用画错了；
- 反之，若参照物本身也在动，那是布局问题（另论）。

**可复用的像素测量法**（截图后按行扫描）：

1. 取一行水平扫描线，找到绘制内容区（如深色面板 `[16,16,16]`）的右边界；
2. 找到嵌入区（如浅色子窗口 `[241,241,241]`）的左边界；
3. 用「子窗口在客户区中的已知 x 偏移」做标定，把图像像素换算成设备像素。

若测得「面板宽度变小、面板与子窗口之间的间隙变大」，比例通常正好等于
`上一帧尺寸 / 新窗口尺寸`——这是 DWM 缩放的直接证据。

> 注意：**不加载任何子窗口时问题往往看不出来**，因为整窗统一缩放、屏幕上没有
> "未缩放的参照物"可对比。这也是这类问题容易被误判为"没问题"的原因。

## 2. 根因：帧尺寸与窗口尺寸无法在同一时刻同时正确

DWM 的合成与应用程序**并发且独立**。无论应用怎么排布
「渲染 → Present → 改窗口尺寸」这三步，都至少留下一个时刻，
**DWM 手上那一帧的尺寸与当时的窗口尺寸不一致**：

| 应用侧顺序 | DWM 可能在何时合成 | 后果 |
|---|---|---|
| 渲染新尺寸 → Present → SetWindowPos | Present 之后、SetWindowPos 之前 | **新尺寸帧**塞进**旧尺寸窗口** → 被缩放 |
| 同上 | SetWindowPos 之后、尚未取到新帧 | **旧尺寸帧**塞进**新尺寸窗口** → 被缩放 |

由此得出三条重要推论：

1. **"消除 Present 阻塞"是错误方向。**
   `Present()` 返回只代表帧已入队，**不代表 DWM 已取到该帧**。
   所以把 Present 从 6ms 降到 0ms（比如预渲染、等待 frame-latency 对象）
   并不会消除第二个时刻——实测中这条路径全部无效。
2. **增加缓冲区数量只能缩短、不能消除**第二个时刻。
3. **应用无法控制"系统何时应用新窗口矩形"**，因此无法让
   「窗口几何变化」与「新帧成为前台」原子化。

换句话说：**只要帧尺寸严格等于窗口尺寸，形变就不可避免**——
因为变化前后窗口有两个尺寸，而同一帧只能有一个尺寸。

## 3. 解法：把帧尺寸与窗口尺寸解耦

唯一正确的方向是让「帧尺寸 ≠ 窗口尺寸」这件事**变得无害**：
不再让 DWM 缩放，而是让它**裁切**。

### 3.1 `DXGI_SCALING_NONE`（核心）

微软文档对 `DXGI_SCALING` 的说明：

- **合法性**：`DXGI_SCALING_NONE` 专为 flip 模型设计——
  只能用于 `DXGI_SWAP_EFFECT_FLIP_SEQUENTIAL` / `FLIP_DISCARD`，
  且通过 `CreateSwapChainForHwnd` / `CreateSwapChainForCoreWindow` /
  `CreateSwapChainForComposition` 创建。（**bitblt 模型不支持**，会返回错误。）
- **行为**：当后备缓冲与呈现目标尺寸不等时，
  缓冲内容 **1:1 呈现、上边缘对齐**，默认**左边缘对齐**（`WS_EX_LAYOUTRTL` 时右对齐），
  目标区域中缓冲之外的部分用**交换链背景色**填充。

于是「过期的旧帧」从**被缩放**变成**被裁切**：内容形状在任何时刻都不改变，
只是可能少显示一块边缘。这正是解法的关键。

```cpp
DXGI_SWAP_CHAIN_DESC1 sd = {};
sd.SwapEffect = DXGI_SWAP_EFFECT_FLIP_DISCARD;
sd.Scaling    = DXGI_SCALING_NONE;          // 关键：不缩放，只裁切
sd.Flags      = DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT;
factory->CreateSwapChainForHwnd(device, hWnd, &sd, NULL, NULL, &swapChain1);
```

### 3.2 后备缓冲「只增不减」

`SCALING_NONE` 保证"缓冲 > 窗口"时是裁切，所以要维持这个不等式：

```cpp
// 只增长，绝不缩小；缩小窗口时缓冲区保持原尺寸
if (w <= g_swapW && h <= g_swapH) return;      // 已覆盖，无需 resize
ResizeBuffers(0, max(w, g_swapW), max(h, g_swapH), DXGI_FORMAT_UNKNOWN, flags);
```

好处不止一个：

- 拖动过程中**不再需要逐步 `ResizeBuffers`**（只在首次超出时增长一次），
  既省掉每步重建 RTV 的开销，也减少了"缓冲重建"带来的不确定性；
- 缓冲超出窗口的部分清成**清屏色**，所以被裁切的边缘是均一色块，**不可见**。

> 踩坑提醒：`ResizeBuffers` 必须传入**与创建时相同的 flags**（尤其是
> `FRAME_LATENCY_WAITABLE_OBJECT`），否则返回 `E_INVALIDARG`、缓冲永不更新。

### 3.3 `SetBackgroundColor()` 兜底

把背景色设为与清屏色一致，兜住"窗口大于缓冲"那一瞬（增长时可能出现一帧）露出的区域：

```cpp
const DXGI_RGBA bg = { 0.15f, 0.15f, 0.15f, 1.0f };
swapChain1->SetBackgroundColor(&bg);
```

### 3.4 布局尺寸与缓冲尺寸解耦

缓冲变大后，**布局仍要按窗口客户区尺寸进行**。以 Dear ImGui 为例，这一点恰好天然支持：

- `imgui_impl_win32` 每帧把 `io.DisplaySize` 设为**窗口客户区**尺寸；
- `imgui_impl_dx11` 在 `RenderDrawData` 时用 `draw_data->DisplaySize`
  设置正交投影与视口——**用的是当帧布局尺寸，不是缓冲尺寸**。

所以在 `ImGui_ImplWin32_NewFrame()` 之后、`ImGui::NewFrame()` 之前覆盖
`io.DisplaySize`，就能"在更大的缓冲左上角按新客户区布局"。
拖动循环里预渲染下一帧时正是这么做的。

### 3.5 降级路径

若 `SCALING_NONE` 创建失败（Win8+ flip 环境下不应发生），应退回
`DXGI_SCALING_STRETCH` + 精确 resize 的旧行为，并记录日志——
**不要因为新 flag 失败就退化到没有交换链**。

## 4. 修复后的残留与进一步方案

残留：**仍可能有"一帧"不一致**，但那一帧上新露出的边缘显示的是**均一清屏色**，
而不是错位或被压扁的内容——远低于可感知阈值。

若这仍不可接受，剩下的方向是：

1. **DirectComposition 自己合成**（`CreateSwapChainForComposition` + DComp visual）：
   把"取帧时机"从 DWM 手里拿回来，可彻底消除残留一帧。复杂度显著上升。
2. **把会被看到形变的内容放进独立子窗口**：
   横向拖动时该子窗口的缓冲不需要 resize，从架构上绕开问题；代价是布局与输入路由改造。

**判据**：`SCALING_NONE` + 只增不减之后，「内容被缩放」这类症状**理论上不可能再出现**
（缓冲恒 ≥ 窗口 ⇒ 缩放比恒为 1）。所以若仍有异常，形态应是"边缘一瞬灰边"而非"内容变窄"，
据此可区分是残留一帧还是新问题。

## 5. 验证方法

| 方法 | 覆盖 | 说明 |
|---|---|---|
| 程序化分步 `SetWindowPos` + 截图扫描 | 缩放路径的**稳态**正确性 | 可完全自动化，无需人工拖动 |
| 关键场景：**大幅缩小** | 证明裁切而非缩放 | 缓冲保持大尺寸、窗口缩小到其 0.4 倍时，若内容仍 1:1 则 `SCALING_NONE` 生效 |
| 人工快速拖动 | **瞬态**观感 | 无法自动化：真实拖动的帧率与步长由系统/人手决定 |
| 日志断言 | 配置是否按预期生效 | 记录交换链 scaling 模式、缓冲增长事件、`ResizeBuffers` 失败 |

自动化脚本见 `scripts/verify_resize_fix.ps1`（本仓库），包含
截图、像素测量、日志断言三部分的完整实现。

> 读日志的坑：应用若用 `fopen(..., "a")` 独占打开日志文件，进程存活期间
> `Get-Content` 会失败，需用 `FileShare.ReadWrite` 打开，或等进程退出后再读。

## 6. 排查清单（避免走弯路）

- [ ] 先用参照物判定：是 **DWM 缩放帧** 还是 **应用布局错误**？
- [ ] 别把时间花在「让 Present 不阻塞」上——Present 返回 ≠ DWM 取帧。
- [ ] 别指望「先渲染好再改窗口尺寸」能解决——两个竞态时刻仍在。
- [ ] 检查 `ResizeBuffers` 的 flags 是否与创建时一致。
- [ ] 确认 `SCALING_NONE` 确实生效（日志打印实际 scaling 模式），
      而不是静默降级到了 STRETCH。
- [ ] 验证时用「窗口远小于缓冲」的场景，最能暴露是否还在缩放。
